## 2026-09-19 — 最初の実測が3倍ずれていた(Chrome 1.33GB → 実際 4.27GB)
- 何が起きたか: `top -l 1 … | awk | python3` の集計で Chrome を「11プロセス 1.33GB」と報告し、計画の前提と Codex への設計依頼の両方に入れた。
  自作の footprint-cli が 30プロセス 4,365MB を返して食い違いが表面化。Apple標準 `/usr/bin/footprint` と 29プロセスを照合して合計差 0.016% で、誤っていたのは top 側と確定。
- 原因: rtk フックがパイプへ流す出力を切り詰めた。`top … > file` では Chrome 行は 26 本あった。
- 捕まえたもの: 賢さではなく、別実装の計器が2つ独立に同じ値を出したこと。
- ルール:
  1. 行数の多いコマンド出力はファイルへ落とし、`wc -l` で入力行数を確認してから集計する。集計結果に入力行数を併記する。
  2. このプロジェクトでメモリを語るときは footprint-cli の値だけを使う。top/ps の目視値を報告に使わない。
  3. 別モデルへ反証を頼む前提の数字は、渡す前に別の手順で1回測り直す(誤った前提を渡すと、相手の結論ごと歪む)。

## 2026-09-19 (2) — osascript quitがテスト対象ではなく本チャンのChromeを巻き込んだ
- 何をしたか: Karu専用プロファイルのテストChrome/Heliumを片付けるつもりで `osascript -e 'tell application "Google Chrome" to quit'` を実行。
- 何が起きたか: これはバンドル単位の終了で、プロファイル別・起動引数別には効かない。本チャンのChrome(pid 32082)も一緒に終了した。
  終了後のChromeは1ウィンドウ9タブに復元されたが、直前の全プロファイル・全ウィンドウの状態と同一かは確認できない。
- ルール:
  1. 複数インスタンスを個別に起動したブラウザ(`--user-data-dir` 付き)を閉じるときは、そのpidを対象にする(`kill <pid>`、要承認)。
     `osascript quit` や Cmd+Q はアプリ全体に効くので、他のインスタンスが動いている可能性があるときは使わない。
  2. [[feedback_do_browser_work_in_background]] の「Chromeを再起動しない」は `--remote-debugging-port` 付き再起動だけの話ではなく、
     osascript quit のような「アプリ全体を巻き込む終了」全般に適用する。
  3. 本チャンのブラウザに影響しうる操作の前は、対象pidが本チャン(ユーザーの通常使用インスタンス)と別であることをpid単位で確認してから実行する。

## 2026-09-20 — JSONDecoderとJSONEncoderのdateStrategy不一致で、プロファイルが毎回作り直されていた
- 何が起きたか: `ProfileStore.save()` は `enc.dateEncodingStrategy = .iso8601` で日付をISO8601文字列として書くのに、
  `loadOrCreate()` の読み込みは既定の `JSONDecoder()`(`.deferredToDate` = Doubleを期待)のままだった。
  型不一致でデコードは必ず失敗し、`try?` で握りつぶされて毎回「新しい既定プロファイルを作る」分岐に落ちる。
  つまり**プロファイルは1回も永続化されていなかった**——毎起動ごとに新しいUUIDのプロファイルが作られ、
  古いプロファイルのCookie/履歴/エンジンルールは全部迷子になっていた。
- 捕まえた経緯: 動作確認のため2つ目のプロファイルを手作業でprofiles.jsonに追記しようとしたら、
  既存の1件が消えて新しい1件だけになった。「あれ、ちゃんと動いてるはずなのに」で終わらせず、
  実際にファイルの中身を読み直したことで発覚。
- ルール:
  1. Codable で日付を含む構造体を保存/復元する時は、encode側とdecode側の `date*Strategy` を**必ず同じ変数か定数で共有**する
     (別々に書くと、片方だけ変更したときに黙って壊れる)。
  2. 「動いているはず」を信じず、保存→再起動→保存前と同じ中身か、を実際に比較する。今回はUUIDが同じかどうかが検証点だった。

## 2026-09-22 — 合成クリックの「0回」を実測値として扱いかけた(当たっていたのは全画面のiTerm2)
- 何が起きたか: 穴越しのクリック透過を測るため CGEvent でクリックし、Heliumのページが受けた回数0を「透過しない」と判定、
  コメントに「実測で0回」と書いた。対策を入れて再測定しても0のまま。クリック直前にその座標の窓の重なりを
  CGWindowListCopyWindowInfo で調べたら、最前面は画面全体を覆う iTerm2 で、Idaten も Helium もそこに無かった。
  ターミナルから起動したアプリには NSApp.activate が効かず、前面に出ていなかった。合成クリック3回は本人のiTerm2に当たっていた。
- ルール:
  1. 画面座標へ入力を送る検査は、送る直前にその座標の最前面の窓の持ち主を確認し、対象アプリでなければ送らない。
  2. 「受けた回数0」は「届かなかった」と「別の窓に当たった」を区別できない。陽性対照(同じ手順で届くと分かっている的)を同じ回に置く。
  3. 本人の画面に物理的な入力を送るのは、本人がその Mac を使っている最中には避ける(今回はフォーカスを奪った可能性がある)。
- 別件(同日): 本人データを隔離するつもりで `HOME=` を差し替えて起動したが、FileManager の applicationSupportDirectory は
  HOME を見ず本物の ~/Library を使った。本人のセッションに1件・履歴に4行を書いてしまい、手で戻した(退避→差分削除→件数確認)。
  隔離が効いたかは、起動後に隔離先にファイルが出来たかで確かめてから操作する。

## 2026-09-23 (2) — 自己検査が本人のブックマークを書き換えた
- 何が起きたか: ブックマークバーの見た目を撮るために、自己検査の中で `bookmarks.add()` を2件呼んだ。
  これはディスクに書く操作で、本人のプロファイル(元は0件)に2件入った。撮った画像で「表示できた」と
  満足しかけたが、ファイルを確認して発覚。削除して元(ファイル無し)に戻した。
- なぜ起きたか: 自己検査はセッションと履歴には「書かない」ガードを入れていたのに、
  ブックマークだけ素通しだった。ガードを「呼ぶ側」に1つずつ足す作りだったので漏れた。
- ルール:
  1. 自己検査・デモ用のモードでは、**表示用の仮データを持たせる**。保存する関数(add/save/record)を呼ばない。
  2. 検査を足したら、走らせた後に「本人のデータが増えていないか」をファイル単位で確認する(件数・mtime)。
  3. 画面が正しく出たことは、データを壊していない証拠にはならない。

## 2026-09-23 (3) — NSApp.terminate で defer が走らず、検査が本人のセッションを上書きした
- 何をしたか: 「タブを失わない」検査で、本人の session.json を退避 → 検査データ200件を書く →
  `defer` で書き戻す、という作りにした。最後に `NSApp.terminate(nil)`。
- 何が起きたか: terminate は関数から戻らないので **defer が実行されない**。さらに
  applicationWillTerminate の自動保存が走り、検査で復元した200件が本人のセッションとして保存された。
  退避ファイル自体も、退避の時点で既に0件で役に立たなかった。最初に取ったバックアップから戻した。
- ルール:
  1. 検査は本人のファイルを**退避して戻す**のでなく、**別のファイルの上でやる**(読み書き先を差し替える)。
     「戻す」処理は、終了・クラッシュ・例外のどれでも確実に走る保証がない。
  2. 検査の後は、本人のファイルが**変わっていないこと**を md5 で確認する。件数だけ見ない。
  3. `NSApp.terminate` の前に後片付けを置かない。置くなら applicationWillTerminate 側に書く。

## 2026-09-23 (4) — 「入れたつもり」で測っていた(CDPで入れた拡張は起動し直すと消える)
- 何をしたか: Chrome に Idaten と同じ休眠拡張を入れて「同じ方針どうし」で比べるため、
  CDP の `Extensions.loadUnpacked` で拡張を入れたプロファイルを用意し、そのプロファイルで Chrome を開いて測った。
- 何が起きたか: 拡張は**その起動の間しか残らない**。開き直すと消えていた(確認したら、居たのは Chrome 内蔵の別物だけ)。
  つまり `chrome_ext` として6組измерした数字は、実質「拡張なしの Chrome」だった。差がほぼ無かったのも当然。
- 気づけた理由: 数字が chrome 条件とほぼ同じだったので、拡張が効いていない可能性を疑って**実際に確かめた**。
  Codex が事前に「再起動後の有効性は要確認」と書いていたのに、確かめる前に測り始めたのが誤り。
- ルール:
  1. 条件を作ったら、**測る前にその条件が成立していることを確かめる**(拡張なら worker が生きているか)。
     成立していなければ測らずに中止する(errors.txt に残す)。
  2. 「入れた」「設定した」は成立の証拠にならない。**測定の直前に、その場で見に行く**。
  3. 実験条件は、成立確認の出力を生データと一緒に保存する(後から「本当にその条件だったか」を確かめられるように)。

## 2026-09-23 (5) — 後から足した設定項目が、書けるのに読めなかった
- 何が起きたか: `Settings.init(from:)` を手書きしていたのに、後から足した `dockChromiumWindow` と
  `bookmarkBarVisible` の復号行を書き忘れていた。`encode` は合成されるので**書き込みはされる**が読み戻されない。
  設定画面で変えても、次の起動で必ず既定に戻っていた。
- ルール: `init(from:)` を手書きする型に項目を足したら、**保存→再読込→同じ値か**を必ず確かめる。
  型が増えるたびに壊れるので、既定値と照合する検査を1つ持っておく。

## 2026-09-23 (6) — 「動画タブを含めた」と言えなかった(どちらのブラウザでも再生されていなかった)
- 何をしたか: 比較計測に固定の動画(60秒mp4・自動再生・ミュート・ループ)を足し、「動画を含む13タブ」として測った。
- 何が分かったか: 状態を記録するようにしたら、**両方のブラウザで `videoPlaying: false`・再生位置0秒**だった。
  前面に出さずに測っている(`open -g`)ので、画面に出ていない窓の再生が止まっていたと見られる。
  両者同じ条件なので比較の公平性は保たれるが、「動画再生中の比較」とは書けない。
- 気づけた理由: Codex の指摘で「同じ作業をさせたと言うには、両者が何を表示・再生していたかの記録が要る」と
  言われ、記録を足したから。**足すまでは「動画あり」と書くつもりだった。**
- ルール:
  1. シナリオに「〜を含む」と書くときは、それが**実際に起きたこと**を各回の記録で示す。
     URL を渡したことは、その状態になったことの証拠ではない。
  2. 記録は数字(メモリ)と同じ生データの中に残す。後から「本当にその条件だったか」を確かめられるように。
  3. 読み込み完了数のような「両者が同じだけ仕事をしたか」の指標も一緒に取る(今回は 7 対 7 で対称だった)。

## 2026-09-23 (7) — 自己検査の「本物かどうか」の判定を間違え、本人のデータに取り込みが走った
- 何が起きたか: 取り込み(Chromium 側のブックマーク・履歴)を「自己検査では走らせない」ようにしたつもりが、
  条件を `selfTestDir == nil || sessionPathOverride != nil` と書いていた。
  `--selftest-session` は**本人のプロファイルの上でセッションファイルだけ差し替える**検査なので、
  2つ目の条件が真になり、取り込みが本人のブックマーク(0→801件)と履歴に対して実行された。
  中身は本人自身の Chromium 側のデータなので実害は小さいが、検査が本人のデータを変えたことに変わりはない。
- ルール:
  1. 「検査中かどうか」の判定は**1つの旗**で決める(`selfTestDir == nil` だけ)。
     「置き場所を差し替えているから本物ではない」のような**間接的な推測を混ぜない**。
  2. 隔離したいなら、プロファイルの置き場所ごと差し替える(`ProfilePaths.directoryOverride`)。
     一部のファイルだけ差し替える検査は「本人のプロファイルの上で動いている」と考える。
