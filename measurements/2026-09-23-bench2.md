# Chrome と Idaten のメモリ比較 第2版(2026-09-23)

第1版(`2026-09-23-chrome-vs-idaten.md`)の穴を埋めた版。生データは `bench2-20260923-124156/`。

## 揃えた条件
- 同じ12ページ + **固定の動画1本**(60秒mp4を 127.0.0.1 から配信。YouTube は配信内容が毎回変わるので使わない)
- どちらも**新品のプロファイル**。Idaten も置き場所ごと差し替え(`--bench-isolated`)。本人のデータには触らない
- 読み込み待ち45秒 → 1秒間隔で採取 → **観測点 60秒 / 300秒 の直前30秒の中央値**(瞬間値1点をやめた)
- 組ごとに順序を入れ替え(奇数組と偶数組で逆)。**6組**
- 値は `ri_phys_footprint`(圧縮・スワップ込み)、単位は MiB
- 機械: MacBook Pro M1 Pro / 16GB / macOS 26.5、Chrome 153.0.8010.54

## 結果(6組)

| 観測点 | | 中央値 MiB | 最小 | 最大 |
|---|---|---|---|---|
| 60秒 | Chrome | 5,870 | 4,886 | 6,343 |
| | Idaten | 529 | 489 | 549 |
| | ペア差 | 5,363 | 4,354 | 5,794 |
| 300秒 | Chrome | 5,845 | 4,578 | 6,997 |
| | Idaten | 511 | 480 | 552 |
| | ペア差 | 5,313 | 4,053 | 6,486 |

- 比(Chrome ÷ Idaten): 60秒で中央値 **11.25**、300秒で **11.41**
- ペア差の中央値の95%区間(組を再標本化): 60秒 4,672〜5,664 MiB / 300秒 4,519〜6,108 MiB
- **6組すべてで Idaten の方が少なかった**

## 言ってよいこと(Codex の査読による)
1. 「この M1 Pro・16GB の環境で、12ページと動画1本を開く手順では、60秒・300秒の両観測点で、
   6組すべて Idaten のメモリフットプリントが小さかった」
2. 「300秒の観測点で、ペアで比べた Chrome − Idaten の差の中央値は約5,313 MiB(約5.2 GiB)だった」
3. 「同じ観測点で、各組の Chrome ÷ Idaten の比の中央値は約11.4だった。別の機械・別のページ構成での比は未検証」

## 言ってはいけないこと
1. 「Idaten は Chrome より11倍軽い」— 指標・条件・比の向きが曖昧で、速度やCPUまで含む一般的な優位に読める
2. 「同じ作業で常に約5GB少なく、機能も性能も同じ」— 同じURLを渡したことと、同じページ状態・再生・操作性能を
   実現したことは別
3. 「同じ休眠方式でも Idaten が省メモリで、エンジンの優位が証明された」— **有効な拡張条件の結果がまだ無い**

## この版でも残っている穴
1. **`chrome_ext`(Chromeに同じ休眠拡張)の数字は使えない**。CDPで入れた拡張は起動し直すと消えるため、
   測っていたのは実質「拡張なしのChrome」だった(実測で確認)。同じプロセス内で
   「入れる→開く→測り終わるまで生かす」形に作り直し、別途計測中
2. 両者が実際に何を表示・再生していたかの記録が、この6組には無い(次の版から記録する)
3. 測定中、本人の Chrome が動いていた(別プロセス群なので合算はしていないが、機械全体の負荷は共有)
4. Chrome の省メモリ機能はタイマーが2〜6時間なので、この時間帯では働いていない
5. メモリ以外の対価(再訪時の読み直し・CPU・通信量)は測っていない

## 必要な組数(Codex の見積もり)
ペア差のばらつきから、**1 GiB の差を検出したいなら5〜6組**、512 MiB なら14〜17組。
今回の6組は前者の水準。10組は妥当な目標だが統計上の必須ではない。
それより「両者が何を表示・再生していたか」の記録の方が、主張の信頼性への効きが大きい。
