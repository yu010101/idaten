--- lessons
  * 変換器の選択は実質ライセンスの選択になる。Swiftネイティブで一番手軽な SafariConverterLib は GPL-3.0、adblock-rust は MPL-2.0 (ただしRust+FFIが必要)、TrackerRadarKit は Apache 2.0 だがEasyList非対応。KaruをOSS配布するときのライセンスを先に決めてから変換器を選ぶ。 https://github.com/AdguardTeam/SafariConverterLib / https://crates.io/api/v1/crates/adblock / https://github.com/duckduckgo/TrackerRadarKit
  * 1リスト150,000ルールが上限 (Apple Frameworks Engineer回答)。EasyList+EasyPrivacy+日本語リストは最初からリスト単位で別々の WKContentRuleList にコンパイルする設計にする。分割すると例外(unblock)ルールがリストをまたいで効かないことがあると SafariConverterLib README が注意している。 https://developer.apple.com/forums/thread/734111 / https://github.com/AdguardTeam/SafariConverterLib/blob/master/README.md
  * WKContentRuleList だけではYouTube広告は止まらない、というのがAdGuard公式の立場 (scriptlet action を WebKit に要望中: bug 225861)。Karuの既定タブでYouTubeを扱うなら document-start のスクリプト注入層が別に要る。作らないなら YouTube は Chromium タブへ回すと割り切る。 https://adguard.com/en/blog/youtube-ads-in-safari-explained.html
  * どの変換器も「変換できないルール」を別出力にするか捨てる。SafariConverterLib は advancedRulesText に分離、adblock-rust は redirect/csp/removeparam/scriptlet/:style()/procedural/entity を CbRuleCreationFailure として落とす。遮断率を Chromium+uBO と同等と見込まない。 https://raw.githubusercontent.com/brave/adblock-rust/master/src/content_blocking.rs
  * adblock-rust の into_content_blocking は FilterSet を debug=true で作らないと Err(()) を返す。試作で最初に踏む罠。 https://raw.githubusercontent.com/brave/adblock-rust/master/src/lists.rs
  * WebKitのルール記法の性能指針: url-filter で量指定子 (* + ?) を避ける、CSSルールは ignore-previous-rules より前に置く、ルールはできるだけ限定的に、正規表現はASCIIのみのサブセット。自作ルールを足すときの基準になる。 https://webkit.org/blog/3476/content-blockers-first-look/
  * Brave iOS は WKWebView制約下で content blocker と JS側の置換を併用しており、「content blocker が JS の置換処理より先にブロックしてしまう」ため一部リクエスト種別でルールを外す必要があると書いている (issue #51342 Open, 2025-12-09)。ルールリストと注入スクリプトを併用するなら同じ競合が起きうる。 https://github.com/brave/brave-browser/issues/51342
  * WebKit は macOS 15.4 から WKWebExtension / WKWebExtensionContext / WKWebExtensionController を公開しており、WebKitベースのブラウザに Web Extension を載せる公式APIがある。「拡張が要る作業だけChromiumタブ」というKaruの前提を一部崩しうるので、段Bの前に評価する価値がある (対応API範囲は今回未確認)。 https://webkit.org/blog/16574/webkit-features-in-safari-18-4/
  * adblockplus/abp2blocklist (JS, GPL-3.0, スター98) は pushed_at が 2019-02-14 で停滞。ABP系の変換器は候補から外してよい。 https://api.github.com/repos/adblockplus/abp2blocklist

--- lessons
  * WKWebExtensionではuBlock Origin(MV2)級の遮断は動かない。Crestの実測では blocking webRequest が不可で、動くのは uBlock Origin Lite(DNR)、Bitwarden、Dark Reader など。Karuの「既定タブは WKContentRuleList で遮断し、拡張が要る作業だけChromiumタブ」という分担は、この限界と整合する。根拠: https://crestbrowser.com/guides/extension-compatibility/
  * WKWebExtensionでChrome拡張を動かすには周辺の自前実装が大量に要る。NookはCRX取得、manifestのWebKit向けパッチ、externally_connectable のpolyfill、native messaging、Bitwarden生体認証の in-process ホストまで書いている。自分用のKaruでは段A(Chromium側に拡張を任せる)のほうが工数が小さい。根拠: https://github.com/nook-browser/Nook/blob/develop/Nook/Managers/ExtensionManager/CLAUDE.md
  * 将来KaruにWKWebExtensionを足す場合の落とし穴は2つ。(1) タブのWKWebViewConfigurationは、controllerを設定済みのconfigurationから .copy() で派生させる。(2) didOpenTab で登録していないタブのcontent scriptメッセージは捨てられる。休眠タブは「url/titleは返すが webView は作らない」アダプタにする。根拠: https://github.com/nook-browser/Nook/blob/develop/Nook/Managers/ExtensionManager/CLAUDE.md
  * WKWebExtension APIの下限は macOS 15.4 (DuckDuckGoは @available(macOS 15.4, iOS 18.4, *))。content scriptsは15.5+とNookの注記にあり、Sumiも15.5を下限にしている。新興のNook / Crest / Vane / Surf は macOS 26 を下限にしている。根拠: https://github.com/duckduckgo/apple-browsers/blob/main/macOS/DuckDuckGo/WebExtensions/Tab%2BWKWebExtensionTab.swift と https://webkit.org/blog
  * タブ休眠の定石は「webView.interactionState を Data で退避 → WKWebViewを破棄 → 復帰時に新しいWKWebViewへ代入」。KestrelとDuckDuckGo (UnloadedTab.interactionStateData) が同じ方式。16GB機のKaruでは、DuckDuckGoと同じく memory pressure critical を契機にし、既定10分未選択のタブを対象とし、除外条件(ピン留め・読込中・音声再生・マイク/カメラ・PDF・PiP)を先に入れる。根拠: https://github.com/duckduckgo/apple-browsers/blob/main/macOS/Duck
  * セッション復元時に全タブを一斉に読み込まない。DuckDuckGoのTabLazyLoaderは同時読込3本、対象最大20本、隣接10本の定数を持ち、選択中タブの読込完了を待ってから始める。非選択タブはWKWebViewを持たない UnloadedTab のまま置く。根拠: https://github.com/duckduckgo/apple-browsers/blob/main/macOS/DuckDuckGo/Tab/TabLazyLoader/TabLazyLoader.swift
  * 段B(CEF同一ウィンドウ埋め込み)は、Chromiumの自前ビルドなしで実例がある。cmuxはビルド済みCEF 151をスクリプトで取得してSHA256で固定している。ただしマージ時点の未解決は、SwiftUIオーバーレイがCEFウィンドウの下に回る、サンドボックス無し(debug)、署名は後続、非表示ペインのdiscard復旧。Karuでも段Bは実験扱いが妥当。根拠: https://github.com/manaflow-ai/cmux/pull/10197
  * ライセンスの地図: コード片を自由に流用できるのは Apache-2.0 (DuckDuckGo、TrackerRadarKit) と MIT (Kestrel、Vane、kaset)。MPL-2.0 (Crest) はファイル単位の公開義務。Nook / Ora / Sumi / Refrax / cmux は GPL-3.0系で、取り込むとKaruもGPL配布になる。OSS配布のライセンスを決める前にGPLコードを混ぜない。根拠: https://api.github.com/repos/duckduckgo/apple-browsers と https://api.github.com/repos/nook-browser/Nook と http
  * 休眠機能を消すとユーザーから不満が出る。Nook 1.0.7 で手動アンロードが削除され、Issue #330 (2026-03-05) に「閉じる=削除になった」という苦情が出た。Karuは手動の「タブを眠らせる」操作を最初から入れる。根拠: https://github.com/nook-browser/Nook/issues/330
